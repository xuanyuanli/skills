# 周报（Weekly Report）

把一段时间内的 git 提交收敛成一份工作周报。

**核心不是罗列 commit，而是回答：这周做成了什么、为什么重要。** 50 次提交通常只值 10–15 条。

## 默认值

| 项 | 默认 | 覆盖方式 |
|---|---|---|
| 仓库 | 当前目录所在仓库 | `--repo` |
| 分支 | 当前分支 | `--branch` |
| 作者 | `git config user.email` | `--author all` 或指定邮箱/姓名 |
| 窗口 | 最近一个周六 00:00 → 现在 | `--since 2026-10-24` |
| 合并提交 | 排除 | 固定 |
| 未提交改动 | 不计入 | 固定 |

## 窗口规则

- 周六为一周起点，按本机时区计算
- 今天就是周六时，回退 7 天，覆盖刚结束的一周，避免空周报
- 用户说「上周」「最近一周」时，按同一规则换算出具体日期，并在标题里写明区间
- 跨月时标题写 `09-27 ~ 10-02`，不写「本周」

## 步骤

### 1. 取数

```bash
cd <技能目录>
python scripts/collect.py --json
```

每条提交包含 `subject`、`body`、`type`、`files`、`insertions`、`deletions`。**`body` 是写价值的主要依据**——很多标题只有十个字，正文才说明为什么改、影响什么。

提交多时加 `--no-stats` 跳过行数统计，速度更快。

### 2. 聚类

把同一工作流的提交合并成一条：

- 同一功能的多天迭代（接口 → 页面 → 修复）
- 同一主题的 `feat` + `fix` + `test`
- 同一模块的连续小改

目标 **8–15 条**；提交少于 10 次时可 3–5 条。宁少勿碎：一条讲清一个完整能力，好过十条讲同一件事。

拿不准怎么合并时，看 [references/example.md](references/example.md) 的对照示例。

### 3. 分层

| 层级 | 判定 | 写法 |
|---|---|---|
| 大功能 | 新增端到端能力、改变业务规则、跨多个模块、有独立入口 | 一句做法 + 一句价值 |
| 小功能 | 单点增强、体验优化、局部规则调整 | 一句做法 + 半句价值 |
| Bug | 缺陷修复、口径补齐、数据对齐 | 具体问题 + 影响 |
| 其他 | 工程、测试、文档、演示、清理 | 合并成 1–2 条 |

`fix` 不一定是 Bug：口径补齐、数据对齐算业务修复，放 Bug 组；构建脚本、测试补强放「其他」。

### 4. 排序

从高到低：

1. 收入与履约链路：下单、支付、结算、违约、退款
2. 核心运营效率：工作台、批量操作、审批流
3. 流量与转化：曝光、排序、漏斗
4. 用户体验：搜索、列表、表单
5. 数据与触达：Push、提醒、报表
6. Bug 修复
7. 工程、文档与其他

同等价值时，影响订单/用户更多的在前。不要按时间排。

### 5. 写价值

价值句回答：**对谁、省了什么、多了什么、少了什么风险。**

- 好：`减少商务手工补录，直付订单能一次跑通到结算`
- 差：`完成了海外直付付款信息功能开发`
- 差：`提升了用户体验`

不编造百分比、时长、金额；只有 commit、统计或用户明确提供的信息里的数字才能写。

### 6. 输出

```markdown
# 周报 · {开始日期} ~ {结束日期}

{一句总览：提交数 + 本期主线}

- **大功能｜{名称}**：{做法}。价值：{价值}。
- **小功能｜{名称}**：{做法}。价值：{价值}。
- **Bug｜{主题}**：{具体问题}。价值：{减少了什么风险}。
- **其他｜{主题}**：{内容}。
```

规则：

- 大功能必须写「价值：」；小功能可只写一句
- Bug 不写「修复若干」，列具体问题
- 「其他」最多 2 条
- 全文 8–15 条，每条 1–2 行
- 需要追溯时在条目末尾附短 hash，如 `（3c0fab7…）`
- 全中文业务表达，不出现 `feat(order):` 这类前缀

### 7. 自检

- [ ] 每条都能对上至少一个 commit
- [ ] 大功能都有明确价值
- [ ] 顺序符合价值层级，不是按时间
- [ ] 没有技术黑话和 commit 前缀
- [ ] 没有未经证实的数字
- [ ] 窗口内的大功能没有被漏掉
- [ ] 条数在 8–15

## 常见错误

1. **逐条翻译 commit**：50 条流水账，没人读得完
2. **按时间排序**：周报要按价值，不按提交顺序
3. **价值写成工作量**：「写了 3000 行」「改了 96 个文件」
4. **把重构/测试混进大功能**：会让真正的大功能失焦
5. **只写功能不写影响**：读者不知道为什么要做
6. **遗漏跨天迭代**：只取最后一天的提交，前面铺的接口全丢了
7. **把未提交改动算进去**：工作区脏不代表已完成

## 边界处理

- **不在 git 仓库**：说明并停止，不要用文件修改时间猜
- **窗口内 0 提交**：输出「本期无提交」，并给一条建议（换分支/作者，或扩大窗口）
- **当前作者无提交、但有他人提交**：提示 `--author all`
- **工作区有未提交改动**：明确说明不计入，只统计已提交内容
- **squash 合并的历史**：标题往往很粗，优先读 `body` 和改动文件
