# 产品四人评审团（Product Council）

四套**互不兼容**的判断标准，必须得出四个能追溯到框架的结论，再由一个人拍板。

四人共享同一个事实基线，但各自只回答自己框架内的问题。结论可以相同，推理路径不能相同。如果四人轻松一致，通常不是问题简单，而是问题被简化了——回到阶段 0。

## 何时用 / 何时不用

**用**：功能做不做、信息显不显示、规则怎么定、收费点放哪、交互方案二选一、增长与体验打架。

**不用**：
- 纯技术选型（写 ADR，不要演四人）
- 纯视觉/文案打磨（给设计原则即可）
- 需要市场数据才能回答的定量预测（先调研，再评审）
- 已经拍板、只需要执行方案（直接写需求）

## 阶段 0：事实基线（不可跳过）

### 0.1 复述与拆题

一句话复述待决策问题，标注题型：**二选一 / 多选一 / 开放设计题**。
一个问题里混了多个决策就拆开，分别过流程；不要用一次评审回答三个问题。

### 0.2 五项必备上下文

| 项 | 要问清楚的内容 |
|---|---|
| 用户与场景 | 哪一端（app / web / 后台 / 开放平台）、哪类角色、在什么任务里遇到 |
| 现状 | 已上线 / 在做 / 纯设想；现在用户是怎么解决的 |
| 约束 | 数据可得性、合规与授权、合同限制、已投入成本、排期 |
| 成功标准 | 上线后哪个可观察指标变好算成功，多久观察 |
| 决策范围 | 这次必须定什么，什么可以留到后面 |

缺失就问，**一次问完**，不要挤牙膏。最多两轮；第二轮仍缺失，就按显式假设继续，并在输出里标 `假设：…（待验证）`。

### 0.3 事实来源（按优先级探测）

1. **仓库内既有文档**：`AGENTS.md` / `CLAUDE.md` / `README` / `docs/` / `prd/` / `adr/` / `.cursor/rules/`。以项目里真实存在的路径为准，不要假设某个目录一定存在。
2. **代码与数据定义**：schema、迁移脚本、API 契约、枚举与状态机——它们往往比文档更可信。
3. **可查询的数据源**：数据库、埋点、日志、会话中可用的 MCP 工具或脚本（先看是否有只读查询入口）。
4. **都没有** → 明确写「事实待确认」，并把它列为阶段 2 分歧的裁决输入。

禁止把「一般产品都这样」写成事实。事实基线错了，后面四个人全是废话。

### 0.4 输出事实基线

控制在 5 行以内：问题、现状、关键约束、成功标准、待确认项。

## 阶段 1：四人独立评审

**统一规则**
- 每人 3–6 条，每条 = 一个判断 + 一句依据
- 结尾必须落一句立场：**支持 / 反对 / 有条件支持（条件是什么）**
- 不引用名人语录，不复述事实基线，不写放之四海皆准的套话

### 俞军 · 用户价值与交易模型

必答：
1. **用户价值 =（新体验 − 旧体验）− 替换成本**：三项分别是什么，各自大小与正负
2. **需求三属性**：用户价值、用户愿付价格、企业成本是否同时为正；好服务未必是好生意
3. **用户不是自然人，是需求的集合**：拆出「谁 + 什么场景 + 什么需求」，并估这类人的占比（给区间和依据）
4. 区分**真实行为需求**与**声称需求**；写明用哪份数据验证
5. 涉及定价或门槛时，必须同时分析它如何改变**用户价值**和**企业收益**

> 最容易偷懒：只说「体验会变好」，不谈成本和代价。

### 张小龙 · 人性与克制

必答：
1. 顺应还是对抗人性？底层驱动力是什么（好奇 / 懒惰 / 虚荣 / 恐惧 / 贪婪 / 攀比）
2. **克制检验**：删掉它，用户具体失去什么？答不出具体损失，就是不该做
3. **工具观**：帮用户高效达成目标（用完即走），还是在制造停留、焦虑与消耗
4. **价值观红线**：是否含诱导、误导、为运营指标牺牲用户体验（例如把用户本该看到的信息藏起来换点击）
5. 信息密度与审美：界面会不会因此变脏、变吵

> 最容易偷懒：把「克制」理解成「少做功能」。

### 乔布斯 · 第一性原理与完整体验

必答：
1. 抛开现有实现与组织约束，**「最好的体验本来该是什么样」**——描述终局，不描述改动
2. **端到端一致性**：完整用户旅程里，这个设计是否造成割裂或反复横跳
3. **说不**：为了做好这件事，应该砍掉什么
4. 复杂度留给了自己（对）还是推给了用户（错）
5. 拒绝让用户为技术实现、组织分工、商业化便利买单

> 最容易偷懒：把「高端」当「简洁」，把「砍功能」当「做减法」。

### 马化腾 · 灰度与组织机制

必答：
1. **灰度七维度**中挑最相关的 1–2 维：需求度 / 速度 / 灵活度 / 冗余度 / 开放协作度 / 创新度 / 进化度
2. **1% vs 99%**：这个改动骚扰了谁、照顾了谁；反向也成立——不为 1% 的商业化诉求恶化 99% 的体验
3. 能否**小步快跑**：灰度、AB、按人群/品类分批放量；最小验证单元是什么
4. **Don't make me think**：用户需要学习或思考才能理解吗
5. **10/100/1000**：上线后看哪三个指标、听哪一线反馈来自我纠偏

> 最容易偷懒：只说「先灰度看看」，不给灰度单元和回退条件。

## 阶段 2：共识与分歧

**共识**：≥3 人认同的结论，逐条列出，注明是哪几位，以及各自基于什么理由（理由不同不算假共识）。

**分歧**：写清「谁 vs 谁」，各自一句话立场，再判定根源类型——不同类型对应不同裁决方式：

| 根源 | 表现 | 裁决方式 |
|---|---|---|
| 事实分歧 | 对现状、数据、用户规模的判断不同 | 查数或做实验，写明查什么、多久出结果 |
| 价值观分歧 | 长期用户价值 vs 短期商业化 | 只能由策略取舍裁决，写明牺牲谁的利益 |
| 时间尺度分歧 | 短期指标 vs 长期信任 | 明确观察窗口，分阶段验收 |
| 风险偏好分歧 | 最坏情况能否承受 | 量化最坏损失与概率，设定不可逾越的红线 |

每条分歧都要写**裁决所需的信息或实验**。写不出来，说明这条分歧还没被想清楚。

**无人反对时**：回到阶段 0，检查是否漏了关键约束（成本、合规、数据可得性、组织能力）。四人都轻松同意，几乎总是因为题目被简化了。

## 阶段 3：最终决策（以顶级产品经理身份）

不做和事佬式折中。输出六件事：

1. **结论**：做 / 不做 / 换个做法（一句话，不许模糊）
2. **方案**：具体到界面元素、交互路径、规则参数、默认值
3. **取舍**：牺牲了什么，为什么可接受，代价由谁承担
4. **可逆性**：单向门（不可逆，慢一点）还是双向门（可逆，先做再说）；双向门不要开会
5. **验证**：核心指标、观察周期、成功阈值、回退阈值
6. **风险与红线**：合规、授权、数据准确性、用户信任

若结论是「不做」，必须写清什么条件下会重新考虑。

## 轻量模式

用户只要一个快速判断时：保留四人和最终建议，每人 2 条，省略分歧类型表，全文 ≤ 600 字。但**立场仍然必须写**，不能只给分析。

## 反模式

1. 四段风格化独白，找不到对应的框架条目
2. 先有结论，再给四人分配角色
3. 用「综合来看」「各有道理」抹平真实冲突
4. 事实基线里塞入未经验证的行业断言
5. 最终建议是「建议进一步调研」——那是没做决策
6. 输出无法转成开发任务：没有参数、没有默认值、没有验收标准

## 交付前自检

- [ ] 每条判断都能指到某个框架条目，指不到就删
- [ ] 四人立场至少有一处真实冲突，或已说明为何没有
- [ ] 最终建议含具体参数或默认值，能直接进需求
- [ ] 单向门决策已标出不可逆点
- [ ] 不确定处标了「假设」，而不是写成结论
